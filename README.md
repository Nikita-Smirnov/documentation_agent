# Product Docs & Onboarding Assistant

Локальный AI-ассистент для генерации и семантического поиска документации с использованием RAG (Retrieval-Augmented Generation) и CrewAI. В текущем виде это ядро более широкого продуктового инструмента: механика генерации, валидации и поиска документации уже реализована и проверена на домене API-документации, дальнейшее развитие переносит её на домен продуктовой документации и онбординга пользователей (см. раздел "Roadmap" ниже).

## О проекте

Итоговая цель проекта: инструмент для продуктовых менеджеров, который позволяет быстро составлять документацию по проекту (обзор продукта и пошаговые инструкции по функциям), а затем даёт пользователям продукта возможность изучать его и задавать вопросы на естественном языке вместо чтения документации целиком. Всё это на полностью локальной инфраструктуре, без обращения к внешним облачным LLM, что важно для компаний, не готовых выгружать внутреннюю документацию в сторонние SaaS-сервисы.

На текущем этапе реализован и протестирован базовый механизм: multi-agent генерация с валидацией формата, инкрементальная индексация и семантический поиск, на домене документации API. Этот домен был выбран как первый шаг, потому что у него простой и однозначно проверяемый формат, что удобно для отладки самой механики генератор-валидатор-поиск до переноса на более сложный и вариативный домен продуктовой документации.

## Описание

AI Docs Assistant (текущая реализация) это веб-сервис на базе FastAPI, который позволяет:

- Генерировать документацию API автоматически с помощью AI-агентов (CrewAI)
- Искать существующую документацию с помощью семантического поиска (RAG)
- Валидировать сгенерированную документацию на соответствие строгому формату
Проект использует:

- Qdrant, векторная база данных для хранения эмбеддингов документации
- Ollama, локальная LLM для генерации текста и создания эмбеддингов
- CrewAI, фреймворк для создания AI-агентов с ролями и задачами
- LangChain, интеграция с векторными хранилищами и эмбеддингами

## Возможности

- Автоматическая генерация документации через двухэтапный процесс (генерация + валидация)
- Семантический поиск по существующей документации
- Проверка дубликатов, система предупреждает, если документ уже существует
- Автоматическое именование файлов на основе содержимого запроса
- Расширенный health-check с проверкой всех зависимостей
- Docker-поддержка для простого развёртывания

## Установка

### 1. Клонирование репозитория

````bash
git clone https://github.com/Nikita-Smirnov/documentation_agent.git
cd documentation_agent
````

### 2. Установка зависимостей

````bash
python -m venv venv
source venv/bin/activate  # На Windows: venv\Scripts\activate
pip install -r requirements.txt
````

### 3. Настройка переменных окружения

Создайте файл `.env` в корне проекта:

````
# Qdrant настройки
QDRANT_HOST=localhost
QDRANT_PORT=6333
QDRANT_COLLECTION_NAME=api_docs
EMBEDDING_MODEL_NAME=mxbai-embed-large # или другая модель для эмбеддингов
VECTOR_SIZE=1024 # Размерность вектора эмбеддингов

API_KEY=ollama
OLLAMA_HOST=127.0.0.1
OLLAMA_PORT=11434
OLLAMA_MODEL=ollama/llama3.1
````

### 4. Запуск Ollama

Убедитесь, что Ollama запущен и у вас установлены необходимые модели:

````bash
ollama pull llama3.1
ollama pull mxbai-embed-large
````

### 5. Запуск через Docker Compose (рекомендуется)

````bash
docker-compose up --build
````

Сервис будет доступен по адресу `http://localhost:8000`.

### 6. Запуск локально

Если вы запускаете локально (без Docker), убедитесь, что Qdrant запущен:

````bash
# Запуск Qdrant через Docker
docker run -p 6333:6333 qdrant/qdrant

# В другом терминале запустите приложение
uvicorn app.main:app --reload
````

## API Эндпоинты

### `GET /health`

Проверка состояния сервиса и всех зависимостей.

Ответ:

````json
{
  "status": "healthy",
  "checks": {
    "qdrant": true,
    "ollama": true,
    "docs": true,
    "rag_canary": true
  }
}
````

### `POST /search`

Семантический поиск по существующей документации.

Запрос:

````json
{
  "query": "эндпоинт для получения профиля пользователя"
}
````

Ответ (найдено):

````json
{
  "found": true,
  "content": "### GET /api/v1/profile\n**Описание**: ..."
}
````

Ответ (не найдено):

````json
{
  "found": false,
  "message": "Документация не найдена. Используйте /generate для создания новой."
}
````

### `POST /generate`

Генерация новой документации API.

Запрос:

````json
{
  "query": "создать эндпоинт для получения списка задач"
}
````

Ответ (успех):

````json
{
  "success": true,
  "message": "Документ успешно создан и сохранён.",
  "content": "### GET /api/v1/tasks\n...",
  "file_path": "docs/get_task.md"
}
````

Ответ (ошибка):

````json
{
  "success": false,
  "message": "Документ уже существует. Используйте /search."
}
````



## Как это работает

### Процесс генерации документации

1. Проверка дубликатов: система проверяет, не существует ли уже похожая документация
2. Генерация: AI-агент (API-документатор) создаёт документацию на основе запроса
3. Валидация: второй AI-агент (валидатор) проверяет соответствие формату
4. Сохранение: валидный документ сохраняется в `docs/` с автоматическим именованием
5. Обновление RAG: векторная база обновляется новым документом
### Семантический поиск

1. Запрос преобразуется в эмбеддинг
2. Выполняется поиск похожих документов в Qdrant
3. Возвращается наиболее релевантный документ, если score выше порога

## Логирование

Логи сохраняются в директории `logs/`:

- `app.log`, все логи приложения
- `errors.log`, только ошибки

## Разработка

### Добавление новых типов сущностей

Для улучшения автоматического именования файлов отредактируйте словари в `app/storage.py`:

````python
ACTION_KEYWORDS = {
    'get': [...],
    'create': [...],
    # добавьте новые действия
}

ENTITY_KEYWORDS = {
    'user': [...],
    'task': [...],
    # добавьте новые сущности
}
````

### Настройка агентов

Параметры агентов (роли, цели, backstory) можно изменить в `app/agents.py`.

### Настройка RAG

Параметры поиска (threshold, количество результатов) настраиваются в `app/rag.py`.

## Roadmap

Следующий шаг развития проекта, ещё не реализован в текущей версии кода:

- Перенос домена с API-документации на продуктовую документацию: два типа документов, обзор проекта (`overview`) и пошаговая инструкция по функции (`guide`), с разными обязательными блоками и разными правилами валидации
- Новый эндпоинт `/ask` для ответа на вопросы пользователя на естественном языке, построенного на найденном контексте (RAG-ответ), в дополнение к существующему `/search`, который возвращает документ целиком
- Явное разделение сценариев продуктового менеджера (автора документации) и пользователя продукта (читателя)
